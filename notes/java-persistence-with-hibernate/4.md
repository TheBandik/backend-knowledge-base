# Глава 4. Отображение хранимых классов

> Зачем читать: ключевая глава – здесь вводится разница между **сущностями** и **типами-значениями**, разбираются первичные ключи, стратегии генерации идентификаторов и настройки уровня класса. Без понимания этого материала невозможно нормально проектировать модель.

---

## 4.1. Сущности и типы-значения

Центральное различие всей ORM-модели:

| Критерий | Сущность (Entity) | Тип-значение (Value Type) |
|---|---|---|
| Идентичность в БД | Есть (PK) | Нет, идентифицируется через владельца |
| Жизненный цикл | Независимый | Зависит от сущности-владельца |
| Разделяемые ссылки | Поддерживает | Не поддерживает |
| Аннотация | `@Entity` | `@Embeddable` или базовый тип |
| Примеры | `User`, `Item`, `Bid` | `Address`, `String`, `BigDecimal` |

**Правило хорошо детализированной модели:** классов больше, чем таблиц. `User` со столбцами `HOME_STREET`, `HOME_CITY`, `HOME_ZIPCODE` – это бедная модель. `User` со свойством `homeAddress: Address` – это правильная детализация.

### Как выбирать?

**Начинай с типа-значения** – переводи в сущность только при крайней необходимости. Сущность нужна, когда:
- на экземпляр нужна **разделяемая ссылка** из нескольких мест
- у объекта **независимый жизненный цикл** (можно существовать без владельца)

**Пример-ловушка:** `Bid` выглядит как тип-значение (принадлежит `Item`), но если в будущем понадобится `User#bids` – это уже разделяемая ссылка, а значит нужна сущность.

**Три следствия при разделении:**
- **Разделяемые ссылки** – предотвращай их для типов-значений; сделай класс неизменяемым, убери публичный сеттер
- **Жизненный цикл** – при удалении `User` удаляется и его `Address` (каскадирование)
- **Идентичность** – классам-сущностям нужен `@Id`, типам-значениям нет

## 4.2. Отображение сущностей с идентичностью

### Три вида идентичности

| Вид | Как определяется |
|---|---|
| Объектная (`==`) | Адрес в JVM |
| Равенство (`equals()`) | Метод `equals()` класса |
| Идентичность в БД | Одинаковый PK в одной таблице |

Все три могут не совпадать. Правильная реализация `equals()` для хранимых классов – нетривиальная задача (обсуждается в главе 10).

### Минимальный класс сущности

```java
@Entity
public class Item {
    @Id
    @GeneratedValue(generator = "ID_GENERATOR")
    protected Long id;

    public Long getId() {
        return id;
    }
    // setter для id НЕ нужен — значение PK никогда не меняется
}
```

- `@Id` над полем → Hibernate обращается ко **всем полям класса напрямую** (не через геттеры)
- Тип идентификатора – `Long` (не `int`/`Integer`): проверка `id == null` удобнее для определения, новый объект или нет; `Integer` кончится через 2 месяца при интенсивной вставке, `Long` – через 300 млн лет

### Требования к первичному ключу

Хороший PK:
- **Not null**
- **Уникален** для каждой записи
- **Неизменяем** — Hibernate не обновляет PK; обновляемые PK сломают кэш и dirty checking

**Натуральные ключи (имя пользователя, номер паспорта)** – плохой выбор: меняются, каскадные UPDATE по FK – кошмар. Лучший выбор – **суррогатный ключ**: технический, не несёт бизнес-смысла, невидим пользователю.

## 4.3. Стратегии генерации идентификаторов

### Стандартные стратегии JPA (`GenerationType`)

| Стратегия | Суть | Когда значение готово |
|---|---|---|
| `AUTO` | Hibernate выбирает сам по диалекту | Зависит от выбранной |
| `SEQUENCE` | Последовательность `HIBERNATE_SEQUENCE` в БД | До INSERT |
| `IDENTITY` | Столбец с автоинкрементом в БД | После INSERT |
| `TABLE` | Таблица `HIBERNATE_SEQUENCES` как счётчик | До INSERT |

> `IDENTITY` – плохо сочетается с батч-вставками: Hibernate не может отложить INSERT, так как значение PK становится известно только после него.

### Рекомендованная конфигурация — `enhanced-sequence`

Определяется один раз на весь пакет в `package-info.java`:

```java
@org.hibernate.annotations.GenericGenerator(
    name = "ID_GENERATOR",
    strategy = "enhanced-sequence",
    parameters = {
        @org.hibernate.annotations.Parameter(
            name = "sequence_name",
            value = "JPWH_SEQUENCE"
        ),
        @org.hibernate.annotations.Parameter(
            name = "initial_value",
            value = "1000"  // тестовые данные используют ID < 1000
        )
    }
)
package org.jpwh.model;
```

Использование во всех классах:
```java
@Id
@GeneratedValue(generator = "ID_GENERATOR")
protected Long id;
```

**Почему `enhanced-sequence`:**
- Если СУБД поддерживает последовательности — использует их
- Если нет — эмулирует через таблицу, поведение одинаковое
- Значение всегда генерируется **до** INSERT → можно сразу вызвать `getId()` после `persist()`
- Один генератор на все классы — порядковость не нарушает уникальность в пределах таблицы

### Полный список стратегий Hibernate (справка)

- `native` – аналог `AUTO` со старым маппингом
- `sequence` – последовательность `HIBERNATE_SEQUENCE`, имя настраивается
- `sequence-identity` – последовательность вызывается во время INSERT
- `enhanced-sequence` – **рекомендован**; sequence или таблица-эмулятор
- `seqhilo` – hi/lo алгоритм поверх sequence (устарел, используй `enhanced-sequence` с оптимизатором)
- `hilo` – hi/lo через таблицу (устарел)
- `enhanced-table` – таблица-счётчик; аналог `TABLE` с новым маппингом
- `identity` – автоинкремент; только через `GenerationType.IDENTITY`
- `increment` – только для single-node приложений с эксклюзивным доступом к БД
- `select` – значение присваивает триггер/дефолт; Hibernate читает его SELECT-ом после INSERT
- `uuid32` – UUID; для глобальной уникальности через несколько БД; `String`/`byte[16]`/`UUID`
- `guid` – UUID через функцию БД (Oracle, MySQL и др.); тип `String`

## 4.4. Настройки на уровне сущности

### 4.4.1. Управление именованием

По умолчанию `@Entity` → имя таблицы = имя класса. Переопределяется через `@Table`:

```java
@Entity
@Table(name = "USERS")  // USER — зарезервированное слово во многих СУБД
public class User { ... }
```

**Экранирование зарезервированных слов:**
```java
@Table(name = "`USER`")           // Hibernate-стиль (обратные кавычки)
@Table(name = "\"USER\"")          // JPA-стиль
```
Hibernate сам подставит нужный вид кавычек по диалекту (`[USER]` для MSSQL, `'USER'` для MySQL и т.д.).

Автоматическое квотирование всех идентификаторов: `hibernate.auto_quote_keyword=true`.

**Кастомная стратегия именования** через `PhysicalNamingStrategy`:

```java
public class CENamingStrategy extends PhysicalNamingStrategyStandardImpl {
    @Override
    public Identifier toPhysicalTableName(Identifier name, JdbcEnvironment ctx) {
        return new Identifier("CE_" + name.getText(), name.isQuoted());
    }
}
```

Регистрация в `persistence.xml`:
```xml
<property name="hibernate.physical_naming_strategy"
          value="org.jpwh.shared.CENamingStrategy"/>
```

**Имена сущностей для JPQL-запросов:**

По умолчанию можно использовать короткое имя класса: `select i from Item i`. При конфликте имён в разных пакетах — переименовать через `@Entity(name = "AuctionItem")`.

### 4.4.2. Динамическое формирование SQL

По умолчанию Hibernate генерирует SQL для всех CRUD-операций **при запуске**. UPDATE всегда включает все столбцы, присваивая им старые значения если изменений не было.

Для таблиц с сотнями столбцов или большим числом сущностей:

```java
@Entity
@org.hibernate.annotations.DynamicInsert
@org.hibernate.annotations.DynamicUpdate
public class Item { ... }
```

- `@DynamicUpdate` → UPDATE содержит только изменившиеся столбцы
- `@DynamicInsert` → INSERT содержит только ненулевые столбцы
- Минус: SQL генерируется при каждом вызове, нет кэша PreparedStatement

### 4.4.3. Неизменяемые сущности

Если экземпляры класса никогда не изменяются после создания (например, `Bid`):

```java
@Entity
@org.hibernate.annotations.Immutable
public class Bid { ... }
```

Hibernate:
- никогда не генерирует UPDATE для таких объектов
- не выполняет dirty checking
- POJO при этом не должен иметь публичных сеттеров

### 4.4.4. Отображение сущности в подзапрос (виртуальное представление)

Когда нельзя добавить VIEW в БД, но нужна агрегированная read-only сущность:

```java
@Entity
@org.hibernate.annotations.Immutable
@org.hibernate.annotations.Subselect(
    "select i.ID as ITEMID, i.ITEM_NAME as NAME, " +
    "count(b.ID) as NUMBEROFBIDS " +
    "from ITEM i left outer join BID b on i.ID = b.ITEM_ID " +
    "group by i.ID, i.ITEM_NAME"
)
@org.hibernate.annotations.Synchronize({"Item", "Bid"}) // имена таблиц для авто-flush
public class ItemBidSummary {
    @Id
    protected Long itemId;
    protected String name;
    protected long numberOfBids;
}
```

`@Synchronize` – Hibernate знает, что перед запросом к `ItemBidSummary` нужно flush-нуть изменения `Item` и `Bid`. Перед `em.find()` синхронизация **не** происходит – только перед JPQL-запросами.

## Главное

- **Сущность** – независимый жизненный цикл, собственный PK, поддерживает разделяемые ссылки. **Тип-значение** – живёт только при владельце, нет PK, ссылки не разделяются
- По умолчанию начинай с типа-значения; переводи в сущность только при необходимости разделяемых ссылок
- `@Id` над полем → Hibernate обращается ко всем полям напрямую; сеттер для `id` не нужен
- Натуральные ключи – плохо; **суррогатный ключ** всегда предпочтительнее
- `IDENTITY` (`AUTO_INCREMENT`) несовместима с батч-вставками – значение известно только после INSERT
- **Рекомендованная стратегия: `enhanced-sequence`** через `@GenericGenerator` в `package-info.java`
- `@Table(name="USERS")` – переопределение имени таблицы; `@Entity(name="AuctionItem")` – переопределение имени для JPQL
- `@DynamicUpdate` / `@DynamicInsert` – SQL генерируется динамически; полезно для таблиц с сотнями столбцов
- `@Immutable` – отключает dirty checking и генерацию UPDATE; используй для неизменяемых данных (лог, аукционные ставки)
- `@Subselect` + `@Synchronize` – виртуальная read-only сущность поверх SQL-запроса, без VIEW в схеме
