# Глава 1. Основы объектно-реляционного отображения

> Зачем читать: фундамент всего, что будет дальше. Объясняет, *почему* ORM вообще существует и какие конкретные проблемы он решает. На собеседовании часто спрашивают именно про несоответствие парадигм.

---

## 1.1. Долговременное хранение (Persistence)

**Persistence** – способность объектов существовать дольше, чем процесс приложения. В контексте Java это означает отображение объектов в таблицы реляционной БД и обратно.

**Почему именно реляционные БД:**
- Единственная универсальная и проверенная технология хранения данных
- Независимость данных от конкретного приложения – данные переживают любое приложение
- Позволяют совместный доступ из нескольких систем
- Гарантии целостности (ACID)

**SQL в Java без ORM – это JDBC:** ручная привязка параметров, итерация по `ResultSet`, копирование значений в объекты. Всё это низкоуровневая рутина, которую ORM берёт на себя.

> Важная оговорка из книги: реляционная модель подходит не всегда. Для распределённых систем с требованиями eventual consistency (CAP-теорема) – NoSQL. Для научных датасетов – специализированные решения. Hibernate не панацея.

---

## 1.2. Несоответствие парадигм (Impedance Mismatch)

Корень всех проблем ORM – фундаментальное различие между объектной и реляционной моделями. Состоит из пяти конкретных проблем.

### 1.2.1. Проблема детализации (Granularity)

**Суть:** в Java можно создавать классы любой степени детализации (`User` → `Address` → `SwissZipCode`). В SQL есть только два уровня: таблицы (созданные тобой) и встроенные типы (`VARCHAR`, `BIGINT` и т.д.).

**Пример:** класс `Address` в Java – отдельная сущность. В БД это нецелесообразно выносить в отдельную таблицу; обычно просто несколько столбцов в `USERS`:

```sql
ADDRESS_STREET VARCHAR(255),
ADDRESS_ZIPCODE VARCHAR(5),
ADDRESS_CITY VARCHAR(255)
```

UDT (User-Defined Types) в SQL теоретически решают это, но на практике непереносимы между СУБД и не стали стандартом.

**Решение в Hibernate:** `@Embeddable` / `@Embedded` (глава 5).

---

### 1.2.2. Проблема подтипов (Subtypes)

**Суть:** Java поддерживает наследование и полиморфизм. SQL – нет (нет стандартного механизма табличного наследования).

**Пример:** `BillingDetails` ← `CreditCard`, `BankAccount`. Ограничение внешнего ключа может ссылаться только на одну конкретную таблицу, полиморфная ассоциация средствами чистого SQL нереализуема.

**Решение в Hibernate:** четыре стратегии отображения наследования (глава 6): одна таблица на иерархию, одна на класс, joined и др.

---

### 1.2.3. Проблема идентичности (Identity)

**Суть:** в Java два понятия – идентичность (`a == b`, адрес в памяти) и равенство (`equals()`). В БД идентичность – значение первичного ключа. Они не совпадают.

**Практические следствия:**
- Два неидентичных Java-объекта могут представлять одну и ту же запись в БД (например, в разных потоках)
- Корректная реализация `equals()` для хранимых классов – нетривиальная задача

**Про первичные ключи:** использовать бизнес-атрибут как PK (например, `USERNAME`) – плохая идея: смена значения тянет за собой каскадное обновление всех FK. Правильный подход – **суррогатный ключ** (скрытый от пользователя, смысла не несёт, только идентифицирует запись).

```sql
-- Плохо: USERNAME как PK
-- Хорошо: суррогатный ID
ID BIGINT NOT NULL PRIMARY KEY,
USERNAME VARCHAR(15) NOT NULL UNIQUE
```

**Решение в Hibernate:** управление идентичностью через `@Id` + стратегии генерации (главы 4, 10).

---

### 1.2.4. Проблема ассоциаций (Associations)

**Суть:** в Java ассоциации – это ссылки (указатели), они направленные. Чтобы сделать связь двунаправленной – нужно объявить её в обоих классах. В SQL ассоциация – значение FK, она не имеет направления (можно делать JOIN в любую сторону).

**Конкретная проблема – many-to-many:** в Java просто `Set<BillingDetails>` с обеих сторон. В SQL требуется промежуточная таблица:

```sql
CREATE TABLE USER_BILLINGDETAILS (
    USER_ID BIGINT,
    BILLINGDETAILS_ID BIGINT,
    PRIMARY KEY (USER_ID, BILLINGDETAILS_ID)
);
```

Этой таблицы нет в предметной модели Java – несоответствие.

**Решение в Hibernate:** `@ManyToMany`, `@JoinTable` (глава 7).

---

### 1.2.5. Проблема навигации по данным (Data Navigation)

**Суть:** в Java данные получают навигацией по графу объектов: `user.getBillingDetails().iterator().next()`. В SQL эффективно получить данные можно только через JOIN с заранее известной глубиной выборки.

**Два крайних варианта, оба плохи:**
- Загрузить всё сразу через JOIN – потенциально огромное декартово произведение, лишние данные в памяти
- Загружать лениво по одному объекту – проблема N+1: одна запись = один SELECT, на 100 записей = 101 запрос

> Проблема N+1 – один из главных источников проблем производительности в Java-приложениях.

**Решение в Hibernate:** стратегии загрузки (lazy/eager), batch fetching, JOIN FETCH (глава 12).

## 1.3. ORM и JPA

**ORM (Object/Relational Mapping)** – автоматическое двустороннее преобразование данных между Java-объектами и таблицами SQL на основе метаданных отображения.

**Важно:** ORM не защищает от SQL, а автоматизирует рутину. Разработчик обязан читать и понимать SQL, который генерирует Hibernate – иначе незаметные проблемы производительности гарантированы.

**Преимущества Hibernate:**
- **Продуктивность** – берёт на себя CRUD-рутину
- **Сопровождаемость** – меньше кода, прослойка между предметной моделью и схемой БД защищает от изменений с обеих сторон
- **Производительность** – кэширование и другие оптимизации "из коробки"
- **Независимость от СУБД** – переносимость между PostgreSQL, MySQL, Oracle и др.

**JPA (Java Persistence API)** – стандартная спецификация, Hibernate является её реализацией. JPA определяет:
- Метаданные отображения (аннотации или XML)
- API для CRUD-операций (`EntityManager`)
- Язык запросов JPQL
- Правила работы с транзакциями, dirty checking, кэшированием

Hibernate реализует JPA и расширяет его собственными возможностями. Можно использовать стандартный JPA API и при необходимости "провалиться" в нативный Hibernate API.

---

## Главное

- **Persistence** – объекты переживают процесс приложения, хранятся в реляционной БД
- **Impedance Mismatch** – фундаментальное несоответствие между объектной и реляционной моделями; делится на 5 проблем: детализация, подтипы, идентичность, ассоциации, навигация
- **Суррогатный ключ** – технический PK без бизнес-смысла; всегда предпочтительнее естественного
- **Проблема N+1** – ленивая загрузка по одному объекту за запрос убивает производительность
- **ORM** не скрывает SQL, а автоматизирует рутину; знать SQL обязательно
- **JPA** – стандарт; **Hibernate** – его реализация с расширениями
- Hibernate не решение для всего: high-load распределённые системы, eventual consistency – смотрим в сторону NoSQL
