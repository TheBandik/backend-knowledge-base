# Глава 11. Транзакции и многопоточность

> Зачем читать: без понимания транзакций невозможно писать корректные JPA-приложения. Оптимистическая блокировка с `@Version` – обязательный вопрос на собеседованиях.

---

## 11.1. Основы транзакций

**ACID:** Atomicity, Consistency, Isolation, Durability.

### JTA и UserTransaction

```java
UserTransaction tx = TM.getUserTransaction();
tx.begin();
// ... работа
tx.commit(); // или tx.rollback()
```

`EntityManager` при создании присоединяется к текущей JTA-транзакции в потоке. Всегда создавать EM после `tx.begin()`.

Если EM создан без активной транзакции – рассинхронизированный режим, автофлаш отключён.

### Обработка исключений

```java
} catch (Exception ex) {
    if (tx.getStatus() == Status.STATUS_ACTIVE
        || tx.getStatus() == Status.STATUS_MARKED_ROLLBACK)
        tx.rollback();
    throw new RuntimeException(ex);
} finally {
    if (em != null && em.isOpen()) em.close();
}
```

Все исключения Hibernate – `RuntimeException` (фатальные). После исключения контекст хранения закрыть, использовать нельзя.

**Нефатальные исключения** (транзакция НЕ помечается на откат):
- `NoResultException` / `NonUniqueResultException`
- `QueryTimeoutException`
- `LockTimeoutException`

**Фатальные:** `EntityNotFoundException`, всё что отмечает транзакцию `STATUS_MARKED_ROLLBACK`.

## 11.2. Управление параллельным доступом

### Проблемы конкурентного доступа

| Проблема | Описание |
|---|---|
| Потерянное изменение | Обе транзакции пишут, одна откатывается – теряется всё |
| Грязное чтение | Транзакция читает неподтверждённые данные другой |
| Неповторимое чтение | Два чтения одного объекта → разные результаты |
| Последняя побеждает | Две транзакции читают → обе пишут → первая затёрта |
| Фантомное чтение | Два одинаковых запроса → разные наборы строк |

### Уровни изоляции ANSI SQL

| Уровень | Грязное чтение | Неповторимое чтение | Фантом |
|---|---|---|---|
| Read Uncommitted | Возможно | Возможно | Возможно |
| **Read Committed** | ❌ | Возможно | Возможно |
| Repeatable Read | ❌ | ❌ | Возможно |
| Serializable | ❌ | ❌ | ❌ |

**Рекомендация:** для JPA-приложений с версионированием достаточно **Read Committed**. Кэш контекста хранения даёт повторимое чтение внутри одной единицы работы. Версионирование решает проблему «последняя побеждает».

## 11.3. Оптимистическое управление конкурентным доступом

### `@Version` – основной инструмент

```java
@Entity
public class Item {
    @Version
    protected long version; // int, Integer, short, Long, Date, Calendar, Timestamp
}
```

Hibernate автоматически:
- увеличивает `version` при изменении сущности
- добавляет `AND VERSION = ?` в `UPDATE` и `DELETE`
- возбуждает `OptimisticLockException` если затронуто 0 строк

Пример генерируемого SQL:
```sql
update ITEM set NAME = ?, VERSION = 1 where ID = ? and VERSION = 0
```

**Что увеличивает версию:**
- изменения полей с типами-значениями
- изменения встраиваемых компонентов
- изменения коллекций `@ElementCollection`

**Что НЕ увеличивает версию:**
- изменения коллекций `@OneToMany(mappedBy=...)` и `@ManyToMany(mappedBy=...)`

**Исключить поле из версионирования:**
```java
@OptimisticLock(excluded = true)
protected String description;
```

### Версионирование с отметкой времени

```java
@Version
protected Date lastUpdated; // java.util.Date, Calendar
// JPA-стандарт: java.sql.Timestamp
```

Менее надёжно: точность JVM (обычно 10-50 мс), кластерная среда без синхронизации времени.

Вариант с временем сервера БД:
```java
@Version
@org.hibernate.annotations.Type(type = "dbtimestamp")
protected Date lastUpdated; // каждое обновление делает SELECT current_timestamp()
```

### Версионирование без отдельного поля (Hibernate)

```java
@Entity
@OptimisticLocking(type = OptimisticLockType.ALL) // или DIRTY
@DynamicUpdate
public class Item { ... }
```

`ALL` – WHERE включает все старые значения всех столбцов. `DIRTY` – только изменившиеся. Не работает с merge в отсоединённом состоянии.

### Ручная проверка версии (`LockModeType.OPTIMISTIC`)

Для обеспечения повторимого чтения при нескольких запросах в одной транзакции:

```java
List<Item> items = em.createQuery("select i from Item i where i.category.id = :id")
    .setLockMode(LockModeType.OPTIMISTIC)
    .setParameter("id", catId)
    .getResultList();
// При flush Hibernate выполнит SELECT для проверки версии каждого Item
// Если версия изменилась → OptimisticLockException
```

## 11.4. Пессимистическое управление конкурентным доступом

Используется когда конфликты часты или нужна немедленная эксклюзивность.

```java
// При find()
Item item = em.find(Item.class, id, LockModeType.PESSIMISTIC_WRITE);

// При явной блокировке
em.lock(item, LockModeType.PESSIMISTIC_WRITE);

// С таймаутом
Map<String, Object> hints = new HashMap<>();
hints.put("javax.persistence.lock.timeout", 5000); // мс
em.find(Item.class, id, LockModeType.PESSIMISTIC_WRITE, hints);
```

| Режим | Описание |
|---|---|
| `PESSIMISTIC_READ` | Разделяемая блокировка; никто не может писать |
| `PESSIMISTIC_WRITE` | Монопольная блокировка; никто не может ни читать, ни писать |
| `PESSIMISTIC_FORCE_INCREMENT` | Монопольная + увеличивает версию |
| `OPTIMISTIC` | Проверка версии при flush |
| `OPTIMISTIC_FORCE_INCREMENT` | Проверка версии + увеличивает версию при flush |
| `READ` | Синоним OPTIMISTIC |
| `WRITE` | Синоним OPTIMISTIC_FORCE_INCREMENT |

## Главное

- ACID: атомарность, непротиворечивость, изолированность, долговечность
- Всегда `tx.begin()` до `createEntityManager()`; откатывать при `STATUS_ACTIVE` или `STATUS_MARKED_ROLLBACK`
- Исключения Hibernate фатальны: контекст закрыть немедленно; нефатальные: `NoResultException`, `QueryTimeoutException`, `LockTimeoutException`
- Рекомендуемый уровень изоляции: **Read Committed** + версионирование
- `@Version` – автоматическое оптимистическое управление; тип `long`/`Long` предпочтителен
- `@Version` генерирует `AND VERSION = ?` в UPDATE/DELETE; при 0 затронутых строк → `OptimisticLockException`
- `@OneToMany(mappedBy=...)` не увеличивает версию; `@OptimisticLock(excluded=true)` – исключить поле
- `OptimisticLockType.ALL` – версионирование без отдельного поля через старые значения в WHERE; не работает с detach/merge
- `LockModeType.OPTIMISTIC` в запросе – проверка версий при flush для обеспечения повторимого чтения
- `PESSIMISTIC_WRITE` – монопольная блокировка на уровне БД; с `lock.timeout` в подсказке
