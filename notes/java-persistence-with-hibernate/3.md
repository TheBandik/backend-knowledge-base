# Глава 3. Модели предметной области и метаданные

> Зачем читать: объясняет, как проектировать хранимые классы (POJO), как правильно реализовывать ассоциации и почему это важно, а также какие варианты задания метаданных ORM существуют и когда что использовать.

---

## 3.1. Многоуровневая архитектура

Классическая трёхуровневая архитектура:

- **Уровень представления** – UI, может обращаться к сущностям предметной модели напрямую
- **Уровень бизнес-логики** – бизнес-правила, оперирует сущностями
- **Уровень хранения** – JPA/Hibernate, сохранение и загрузка данных

Правила: зависимости только сверху вниз, каждый уровень знает только об интерфейсе нижележащего.

**Сквозные задачи** (журналирование, транзакции, авторизация) – не принадлежат ни одному уровню, реализуются инфраструктурно.

---

## 3.2. Требования к хранимым классам (POJO)

Хранимый класс должен быть максимально независим от инфраструктуры. Это называется **прозрачностью хранения** (transparent persistence): класс не знает, что он может сохраняться.

**Обязательные требования JPA:**
- Конструктор без аргументов (минимум package-private) – Hibernate использует рефлексию для создания экземпляров
- Класс не финальный, методы не финальные (нужны для прокси)
- Идентифицирующий атрибут (`@Id`)
- Поля-коллекции объявлять через интерфейс (`Set`, `List`, `Collection`), не через конкретный тип (`HashSet`)

**Рекомендации:**
- Поля – `protected` (не `private`, не `public`)
- Методы доступа (getter/setter) в стиле JavaBean
- Инициализировать коллекции при объявлении (`= new HashSet<>()`) – избегает `NullPointerException`

### Dirty checking и методы доступа

Hibernate сравнивает **значения**, а не ссылки – можно возвращать из геттера `new String(value)`, UPDATE не будет:

```java
public String getFirstname() {
    return new String(firstname); // OK
}
```

**Исключение:** для коллекций проверяется **идентичность**. Геттер должен возвращать ту же коллекцию, что была передана в сеттер, иначе будет лишний UPDATE.

```java
// Плохо, если Hibernate работает через методы доступа:
public List<String> getNames() {
    return Arrays.asList(names); // новый объект каждый раз!
}
```

## 3.3. Реализация ассоциаций

**JPA не управляет ассоциациями автоматически.** Если связь двунаправленная – нужно поддерживать обе стороны вручную.

Неправильно (только одна сторона):
```java
anItem.getBids().add(aBid); // не устанавливает aBid.item
```

Правильно:
```java
anItem.getBids().add(aBid);
aBid.setItem(anItem);
```

**Лучшая практика – вспомогательный метод:**

```java
// В классе Item
public void addBid(Bid bid) {
    if (bid == null) throw new NullPointerException("Can't add null Bid");
    if (bid.getItem() != null) throw new IllegalStateException("Bid already assigned");
    getBids().add(bid);
    bid.setItem(this);
}
```

Это гарантирует целостность с обеих сторон и упрощает код клиента. `setBids()` при этом можно сделать `private`.

**Правило проверки:** при непонимании поведения ассоциаций в JPA – спроси себя: «Что бы я сделал без Hibernate?» Hibernate не меняет обычную семантику Java.

## 3.4. Метаданные отображения: варианты

### Аннотации JPA (предпочтительный вариант)

```java
import javax.persistence.Entity;

@Entity
public class Item {
    // все поля автоматически становятся хранимыми
}
```

**Преимущества:** типобезопасность, рефакторинг работает, близко к коду, проверяется IDE.

**Аннотации Hibernate** – для возможностей, недоступных в стандарте JPA:

```java
@Entity
@org.hibernate.annotations.Cache(
    usage = org.hibernate.annotations.CacheConcurrencyStrategy.READ_WRITE
)
public class Item { ... }
```

Соглашение: писать полное имя пакета `org.hibernate.annotations.X` – сразу видно, что это не стандарт.

**Глобальные аннотации** (например, `@NamedQuery`) – хранить в `package-info.java`:

```java
@org.hibernate.annotations.NamedQueries({
    @org.hibernate.annotations.NamedQuery(
        name = "findItemsOrderByName",
        query = "select i from Item i order by i.name asc"
    )
})
package org.jpwh.model.querying;
```

> Аннотации JPA не поддерживают уровень пакета – для `package-info.java` использовать аннотации Hibernate.

### Bean Validation (JSR 303)

Аннотации валидации из `javax.validation.constraints`:

```java
@NotNull
@Size(min = 2, max = 255, message = "Name is required, maximum 255 characters.")
protected String name;

@Future
protected Date auctionEnd;
```

**Интеграция с Hibernate:**
- При наличии Hibernate Validator в classpath – автоматически валидирует перед INSERT/UPDATE
- `@NotNull` → `NOT NULL` в DDL
- `@Size(max=255)` → `VARCHAR(255)` в DDL
- Управление через `<validation-mode>` в `persistence.xml`: `AUTO` (по умолчанию), `CALLBACK`, `NONE`

### XML-метаданные

**`META-INF/orm.xml`** – стандарт JPA, синтаксис зеркалит аннотации:

```xml
<entity class="org.jpwh.model.simple.Item" access="FIELD">
    <attributes>
        <basic name="name">
            <column name="ITEM_NAME"/>
        </basic>
    </attributes>
</entity>
```

Если добавить `<xml-mapping-metadata-complete/>` – все аннотации в классах игнорируются.

**`.hbm.xml`** – нативный формат Hibernate (устарел как основной, но полезен для специфичных настроек: кастомные типы, DDL-хелперы, динамические фильтры).

**Когда XML:**
- Метаданные зависят от среды развёртывания
- Нужны глобальные настройки без привязки к конкретному классу
- Legacy-проекты

## Главное

- **Прозрачность хранения** – хранимый класс не знает о Hibernate; зависимость от JPA только на compile time
- Конструктор без аргументов – обязателен (используется рефлексией)
- Классы и методы не финальные – нужны для прокси
- Коллекции объявлять через интерфейс (`Set`, `List`), инициализировать сразу
- **JPA не управляет двунаправленными ассоциациями** – поддерживать обе стороны вручную; вспомогательный метод `addBid()` – best practice
- Dirty checking коллекций сравнивает по **ссылке**, обычных полей – по значению
- Аннотации JPA (`javax.persistence`) – стандарт; аннотации Hibernate – расширение с полным именем пакета
- Bean Validation интегрируется автоматически: аннотации влияют и на валидацию, и на DDL-схему
- XML (`orm.xml`) – для переопределений и настроек зависящих от деплоя; `.hbm.xml` – нативный Hibernate, legacy
