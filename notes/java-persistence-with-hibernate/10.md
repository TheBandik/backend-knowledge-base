# Глава 10. Управление данными

> Зачем читать: самая важная глава для понимания работы JPA. Жизненный цикл сущностей, контекст хранения, `EntityManager` API – всё это спрашивают на каждом собесе.

---

## 10.1. Жизненный цикл сущностей

Четыре состояния экземпляра:

| Состояние | Описание | Как попасть |
|---|---|---|
| **Временное** (transient) | Создан `new`, нет связи с БД | Создание через `new` |
| **Хранимое** (persistent/managed) | Связан с контекстом хранения, отслеживается | `persist()`, `find()`, `merge()`, каскад |
| **Удалённое** (removed) | Помечен для удаления | `remove()` |
| **Отсоединённое** (detached) | Был managed, контекст закрыт/`detach()` | Закрытие EM, `detach()`, `clear()` |

### Контекст хранения (Persistence Context)

- Создаётся при `emf.createEntityManager()`, закрывается при `em.close()`
- Следит за всеми managed-экземплярами (dirty checking)
- Является **кэшем первого уровня** – нельзя отключить
- Гарантирует **область объектной идентичности**: в одном контексте `em.find(Item.class, id) == em.find(Item.class, id)` – всегда `true`
- При загрузке повторного запроса с тем же ID Hibernate не идёт в БД – возвращает закэшированный объект

**Важно:** при `FlushModeType.AUTO` (по умолчанию) Hibernate выталкивает контекст перед каждым JPQL-запросом. При `FlushModeType.COMMIT` – только при commit.

## 10.2. API EntityManager

### Каноническая форма единицы работы

```java
EntityManager em = null;
UserTransaction tx = TM.getUserTransaction();
try {
    tx.begin();
    em = JPA.createEntityManager();
    // работа с данными
    tx.commit();
} catch (Exception ex) {
    if (tx.getStatus() == Status.STATUS_ACTIVE
        || tx.getStatus() == Status.STATUS_MARKED_ROLLBACK)
        tx.rollback();
    throw new RuntimeException(ex);
} finally {
    if (em != null && em.isOpen()) em.close();
}
```

### Основные операции

**`persist(entity)`** – временный → managed. INSERT выполняется при flush/commit. Значение PK присваивается сразу, если генератор работает до INSERT (`enhanced-sequence`).

**`find(Class, id)`** – загрузка по PK. Всегда обращается в БД если нет в кэше. Возвращает `null` если не найдено.

**`getReference(Class, id)`** – возвращает прокси без SELECT. Инициализируется при первом обращении к полю (кроме `getId()`). Если записи нет – `EntityNotFoundException` при инициализации. Если уже есть в кэше – возвращает реальный объект.

```java
PersistenceUnitUtil pu = emf.getPersistenceUnitUtil();
assertFalse(pu.isLoaded(proxy)); // проверить инициализацию
Hibernate.initialize(proxy);    // принудительная инициализация
```

**`merge(entity)`** – отсоединённый → managed (копирование состояния). Возвращает managed-экземпляр; исходную ссылку надо заменить. Работает и с временными объектами (создаёт новый). Не модифицирует переданный объект.

**`remove(entity)`** – managed → removed. DELETE при flush/commit. Требует полностью инициализированного объекта (если передан прокси – выполнит SELECT).

**`detach(entity)`** – вручную отсоединить один экземпляр.

**`clear()`** – отсоединить весь контекст.

**`contains(entity)`** – проверить, является ли managed.

**`refresh(entity)`** – перезагрузить из БД, перезаписав изменения в памяти.

**`flush()`** – принудительная синхронизация с БД (без commit).

### Режим только для чтения

```java
// Весь контекст – без dirty checking
em.unwrap(Session.class).setDefaultReadOnly(true);

// Один экземпляр
em.unwrap(Session.class).setReadOnly(item, true);

// Запрос
em.createQuery("...").setHint(QueryHints.READ_ONLY, true);
```

> Копии не создаются → меньше памяти → нет UPDATE при flush.

## 10.3. Отсоединённое состояние и идентичность

После закрытия контекста объекты становятся detached. Два объекта из разных контекстов с одинаковым PK не идентичны (`!=`) и не равны по умолчанию (`equals()` из `Object`).

### Когда нужен кастомный `equals()`/`hashCode()`

Только если:
- используешь detached-объекты в `Set` или как ключи `Map`
- сравниваешь объекты из разных контекстов

**Решение – бизнес-ключ:** уникальное поле с бизнес-смыслом (часто с `UNIQUE` в БД).

```java
@Override
public boolean equals(Object other) {
    if (this == other) return true;
    if (other == null) return false;
    if (!(other instanceof User)) return false;  // instanceof, не getClass()!
    User that = (User) other;
    return this.getUsername().equals(that.getUsername()); // через геттер, не поле!
}

@Override
public int hashCode() {
    return getUsername().hashCode();
}
```

**Почему `instanceof` а не `getClass()`:** другой может быть прокси-объектом (подкласс).
**Почему геттер а не поле:** прокси-объект не даёт прямого доступа к полям.
**Почему не `getId()`:** при добавлении временного объекта в Set id = null → hashCode изменится после persist → нарушение контракта Set.

### Критерии хорошего бизнес-ключа

- Неизменяемый атрибут (или редко меняющийся)
- Имеет ограничение `UNIQUE` в БД
- Метка времени создания (с осторожностью – точность JVM)
- PK связанной сущности (если связанный объект уже persistent)

### Слияние (`merge`)

```java
detachedUser.setUsername("johndoe");
tx.begin();
em = JPA.createEntityManager();
User mergedUser = em.merge(detachedUser); // detachedUser остаётся detached
mergedUser.setUsername("doejohn");        // работать только с mergedUser
tx.commit();
```

Процесс `merge`: Hibernate ищет объект в контексте → если нет, загружает из БД → копирует поля detached → возвращает managed. После `merge` ссылка на detached-объект устаревает.

## Главное

- Четыре состояния: **transient → persistent → removed** (+ **detached**)
- Контекст хранения = кэш первого уровня; нельзя отключить; область объектной идентичности
- `find()` возвращает инициализированный объект или null; `getReference()` возвращает прокси без SELECT
- `persist()` → INSERT при flush; `merge()` → возвращает managed-копию, исходная ссылка устаревает
- Dirty checking – автоматически; `flush()` – принудительно; по умолчанию перед JPQL-запросами и при commit
- `FlushModeType.COMMIT` – отключить flush перед запросами
- `setDefaultReadOnly(true)` / `setReadOnly(obj, true)` – отключить dirty checking для экономии памяти
- `detach()` / `clear()` – вручную очистить контекст во избежание `OutOfMemoryException`
- `equals()`/`hashCode()` через бизнес-ключ – только если detached-объекты используются в Set/Map
- В `equals()` всегда `instanceof` (не `getClass()`) и геттеры (не поля) для совместимости с прокси
- Не использовать `getId()` в `equals()`/`hashCode()` – id null до persist
