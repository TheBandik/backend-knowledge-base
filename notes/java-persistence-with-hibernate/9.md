# Глава 9. Сложные и унаследованные схемы

> Зачем читать: DDL-аспекты, о которых спрашивают реже, но знать нужно. Составные ключи – частый вопрос при работе с legacy-БД. Ограничения, индексы и вторичные таблицы – полезно при проектировании.

---

## 9.1. Управление генерацией схемы

Hibernate генерирует DDL из метаданных отображения. **Правило:** никогда не запускать приложение в рабочей среде без проверки сгенерированной схемы администратором БД.

### SQL-сценарии в `persistence.xml`

Три типа сценариев:
- **create-script** – выполняется во время/до/после генерации таблиц
- **drop-script** – при удалении схемы
- **load-script** – всегда после создания всех таблиц (импорт тестовых данных, дополнительные `ALTER TABLE`)

```xml
<property name="hibernate.hbm2ddl.import_files_sql_extractor"
          value="org.hibernate.tool.hbm2ddl.MultipleLinesSqlCommandExtractor"/>
<!-- скрипт создания ПЕРЕД генерацией таблиц Hibernate -->
<property name="javax.persistence.schema-generation.create-source"
          value="script-then-metadata"/>
<property name="javax.persistence.schema-generation.create-script-source"
          value="complexschemas/CreateScript.sql.txt"/>
<!-- скрипт загрузки тестовых данных -->
<property name="javax.persistence.sql-load-script-source"
          value="complexschemas/LoadScript.sql.txt"/>
```

Значения `create-source`: `metadata`, `script`, `metadata-then-script`, `script-then-metadata`.

## 9.2. Ограничения SQL

Четыре уровня ограничений в SQL:
- **Домена** – тип данных и его допустимые значения
- **Столбца** – `NOT NULL`, `CHECK` для одного столбца
- **Таблицы** – `UNIQUE` по нескольким столбцам, `CHECK` для нескольких столбцов одной строки
- **БД** – `FOREIGN KEY`, `CHECK` по нескольким таблицам

> Исключение `ConstraintViolationException` – не для валидации пользовательского ввода. Это сигнал об ошибке приложения для разработчика. Используй Bean Validation для пользователя.

### Ограничения домена и столбца

Пользовательский SQL-домен в сценарии создания:
```sql
create domain if not exists EMAIL_ADDRESS as varchar
check (position('@', value) > 1);
```

Применение в отображении через `columnDefinition`:
```java
@Column(nullable = false, unique = true, columnDefinition = "EMAIL_ADDRESS(255)")
protected String email;

@Column(columnDefinition = "varchar(15) not null unique check (not substring(lower(USERNAME), 0, 5) = 'admin')")
protected String username;
```

### Табличные ограничения

```java
@Entity
@org.hibernate.annotations.Check(constraints = "AUCTIONSTART < AUCTIONEND")
public class Item { ... }

@Entity
@Table(name = "USERS",
    uniqueConstraints = @UniqueConstraint(
        name = "UNQ_USERNAME_EMAIL",
        columnNames = {"USERNAME", "EMAIL"}
    )
)
public class User { ... }
```

### Ограничения уровня БД (несколько таблиц)

Через сценарий загрузки (после создания всех таблиц):
```sql
alter table BID add constraint AUCTION_BID_TIME
check (CREATEDON <= (select i.AUCTIONEND from ITEM i where i.ID = ITEM_ID));
```

### Именование внешних ключей

```java
@ManyToOne
@JoinColumn(name = "ITEM_ID", nullable = false,
    foreignKey = @ForeignKey(name = "FK_ITEM_ID"))
protected Item item;
```

Атрибут `foreignKey` поддерживается в `@PrimaryKeyJoinColumn`, `@JoinTable`, `@CollectionTable`, `@MapKeyJoinColumn`.

## 9.3. Индексы

```java
@Entity
@Table(name = "USERS", indexes = {
    @Index(name = "IDX_USERNAME", columnList = "USERNAME"),
    @Index(name = "IDX_USERNAME_EMAIL", columnList = "USERNAME, EMAIL")
})
public class User { ... }
```

> Не добавляй индекс «на всякий случай» – только после анализа реальных планов выполнения запросов.

## 9.4. Унаследованные первичные ключи

### Натуральный первичный ключ

Если в legacy-схеме PK – это `USERNAME`:
```java
@Entity
@Table(name = "USERS")
public class User {
    @Id  // без @GeneratedValue – приложение само присваивает значение
    protected String username;
}
```

### Составной первичный ключ (`@EmbeddedId`)

Отдельный класс-идентификатор – `@Embeddable` + `Serializable` + `equals()` + `hashCode()`:

```java
@Embeddable
public class UserId implements Serializable {
    protected String username;
    protected String departmentNr;
    // конструкторы, equals(), hashCode()
}

@Entity
@Table(name = "USERS")
public class User {
    @EmbeddedId
    protected UserId id;
}
```

Использование:
```java
UserId id = new UserId("johndoe", "123");
User user = em.find(User.class, id);
```

### FK внутри составного PK (`@MapsId`)

Когда часть составного PK является FK на другую таблицу:
```java
@Entity
@Table(name = "USERS")
public class User {
    @EmbeddedId
    protected UserId id; // UserId.departmentId – Long

    @ManyToOne
    @MapsId("departmentId") // Hibernate берёт значение из Department, игнорирует UserId#departmentId
    protected Department department;
}
```

Альтернатива через `insertable=false, updatable=false` (предпочтительнее):
```java
@ManyToOne
@JoinColumn(name = "DEPARTMENTID", insertable = false, updatable = false)
protected Department department;
// управление столбцом через UserId#departmentId
```

### FK на составной PK (`@JoinColumns`)

```java
@ManyToOne
@JoinColumns({
    @JoinColumn(name = "SELLER_USERNAME",    referencedColumnName = "USERNAME"),
    @JoinColumn(name = "SELLER_DEPARTMENTNR", referencedColumnName = "DEPARTMENTNR")
})
protected User seller;
```

> Всегда указывать `referencedColumnName` при `@JoinColumns` – без него порядок столбцов может быть некорректным.

### FK на не-PK столбец

```java
@ManyToOne
@JoinColumn(name = "SELLER_CUSTOMERNR", referencedColumnName = "CUSTOMERNR")
protected User seller;
```

## 9.5. Вторичные таблицы (`@SecondaryTable`)

Свойства одной сущности в двух разных таблицах:

```java
@Entity
@Table(name = "USERS")
@SecondaryTable(
    name = "BILLING_ADDRESS",
    pkJoinColumns = @PrimaryKeyJoinColumn(name = "USER_ID")
)
public class User {
    protected Address homeAddress; // в основной таблице USERS

    @AttributeOverrides({
        @AttributeOverride(name = "street",
            column = @Column(table = "BILLING_ADDRESS", nullable = false)),
        @AttributeOverride(name = "city",
            column = @Column(table = "BILLING_ADDRESS", nullable = false))
    })
    protected Address billingAddress; // в таблице BILLING_ADDRESS
}
```

> `@AttributeOverride` замещает все аннотации из встраиваемого класса – нужно повторять `nullable` и `length` явно.

## Главное

- Никогда не разворачивать схему в production без ревью администратора БД
- `load-script` – лучшее место для `ALTER TABLE` с межтабличными ограничениями CHECK
- `@Column(columnDefinition=...)` – прямой SQL в DDL, привязывает к конкретной СУБД
- `@org.hibernate.annotations.Check` – табличное ограничение CHECK в `CREATE TABLE`
- `@Table(uniqueConstraints=...)` – именованные UNIQUE на несколько столбцов
- `@ForeignKey(name=...)` – именование FK-ограничений для читаемых сообщений об ошибках
- Натуральный PK – без `@GeneratedValue`; приложение присваивает значение само
- `@EmbeddedId` – составной PK: отдельный `@Embeddable` класс с `equals()`/`hashCode()`
- `@MapsId("field")` – часть составного PK является FK; предпочтительнее – `insertable=false, updatable=false`
- `@JoinColumns` + `referencedColumnName` – FK на составной PK; `referencedColumnName` обязателен
- `@SecondaryTable` – свойства одной сущности в двух таблицах; только для legacy-схем
