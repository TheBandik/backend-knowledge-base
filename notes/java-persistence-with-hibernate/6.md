# Глава 6. Отображение наследования

> Зачем читать: самое частое место на собесах по JPA. Нужно знать все четыре стратегии, их SQL, плюсы/минусы и критерии выбора. Здесь же – работа с прокси при полиморфных ассоциациях.

---

## 6.1. Проблема наследования в реляционной модели

Java поддерживает отношения **is-a** (наследование) и **has-a** (ссылка). SQL поддерживает только **has-a**. Это и есть корень несоответствия. Четыре стратегии решают эту проблему по-разному – с разными компромиссами.

---

## 6.2. Стратегия 1: `@MappedSuperclass` – неявный полиморфизм

Суперкласс не является сущностью. Каждый конкретный подкласс отображается в **собственную независимую таблицу**, которая содержит все столбцы, включая унаследованные.

```java
@MappedSuperclass
public abstract class BillingDetails {
    @NotNull
    protected String owner;
}

@Entity
@AttributeOverride(name = "owner", column = @Column(name = "CC_OWNER", nullable = false))
public class CreditCard extends BillingDetails {
    @Id
    @GeneratedValue(generator = Constants.ID_GENERATOR)
    protected Long id;
    // ...
}
```

**Схема:** две независимые таблицы `CREDITCARD` и `BANKACCOUNT` без общей родительской.

**Генерируемый SQL для запроса по суперклассу:** два отдельных SELECT – по одному на каждый конкретный класс.

| | |
|---|---|
| ✅ | Простота, запросы к конкретным классам быстрые |
| ❌ | Нет полиморфных ассоциаций (нет таблицы `BILLINGDETAILS` для FK) |
| ❌ | Изменение суперкласса → изменение столбцов во всех таблицах |
| ❌ | Нельзя наложить общие ограничения целостности |

**Когда использовать:** верхушка иерархии, где полиморфизм не нужен и суперкласс стабилен.

> **Ограничение:** `@MappedSuperclass` не является `@Entity`. Нельзя написать `select bd from BillingDetails bd` – Hibernate не знает такой сущности. Нельзя иметь ассоциацию `@ManyToOne` на `BillingDetails`.

---

## 6.3. Стратегия 2: `TABLE_PER_CLASS` – UNION

Суперкласс становится `@Entity`. Каждый конкретный класс также имеет собственную таблицу со всеми столбцами включая унаследованные. Схема – та же что и в `@MappedSuperclass`, но теперь суперкласс известен Hibernate как сущность.

```java
@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class BillingDetails {
    @Id  // @Id обязателен в суперклассе
    @GeneratedValue(generator = Constants.ID_GENERATOR)
    protected Long id;
    @NotNull
    protected String owner;
}

@Entity
public class CreditCard extends BillingDetails {
    protected String cardNumber;
    // ...
}
```

**SQL для `select bd from BillingDetails bd`:** `UNION ALL` из обеих таблиц с `null`-заглушками для чужих столбцов и числовым литералом `CLAZZ_` для определения типа:
```sql
select ID, OWNER, EXPMONTH, EXPYEAR, CARDNUMBER,
       ACCOUNT, BANKNAME, SWIFT, CLAZZ_
from (
    select ID, OWNER, EXPMONTH, EXPYEAR, CARDNUMBER,
           null as ACCOUNT, null as BANKNAME, null as SWIFT, 1 as CLAZZ_
    from CREDITCARD
    union all
    select id, OWNER, null, null, null,
           ACCOUNT, BANKNAME, SWIFT, 2 as CLAZZ_
    from BANKACCOUNT
) as BILLINGDETAILS
```

| | |
|---|---|
| ✅ | Полиморфные запросы и ассоциации работают |
| ✅ | NOT NULL ограничения поддерживаются в каждой таблице |
| ❌ | `TABLE_PER_CLASS` **не обязательна** по стандарту JPA – может не поддерживаться |
| ❌ | UNION дорогой, сложный SQL |
| ❌ | Дублирование столбцов суперкласса, эволюция схемы сложная |

---

## 6.4. Стратегия 3: `SINGLE_TABLE` – одна таблица на иерархию

Вся иерархия в **одной таблице**. Строки различаются по столбцу-**селектору** (`discriminator`).

```java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "BD_TYPE") // по умолчанию DTYPE
public abstract class BillingDetails {
    @Id
    @GeneratedValue(generator = Constants.ID_GENERATOR)
    protected Long id;

    @NotNull
    @Column(nullable = false) // @NotNull одного недостаточно – Hibernate игнорирует при DDL!
    protected String owner;
}

@Entity
@DiscriminatorValue("CC") // всегда указывать явно
public class CreditCard extends BillingDetails {
    @NotNull // Hibernate проверяет в runtime, но NOT NULL в DDL не создаст
    protected String cardNumber;
    // ...
}
```

**SQL для `select bd from BillingDetails bd`:** один простой SELECT со всеми столбцами. Для запроса к подклассу добавляется `where BD_TYPE='CC'`.

**Нет столбца-селектора в legacy-схеме** – заменяется формулой:
```java
@org.hibernate.annotations.DiscriminatorFormula(
    "case when CARDNUMBER is not null then 'CC' else 'BA' end"
)
```

| | |
|---|---|
| ✅ | Лучшая производительность – нет JOIN/UNION |
| ✅ | Простые запросы, удобно писать отчёты вручную |
| ✅ | Простая эволюция схемы |
| ❌ | Столбцы подклассов **не могут быть NOT NULL** (кроме полей суперкласса) |
| ❌ | Нарушение 3NF – функциональные зависимости между не-ключевыми столбцами |
| ❌ | При широких иерархиях – много NULL-столбцов |

> **Ловушка:** `@NotNull` на полях подклассов при `SINGLE_TABLE` – Hibernate проверяет их в runtime перед INSERT, но DDL-ограничения `NOT NULL` **не создаёт**. Данные из других приложений могут быть некорректными.

## 6.5. Стратегия 4: `JOINED` – таблица на каждый подкласс

Каждый класс иерархии – своя таблица. Таблица подкласса содержит только **собственные** столбцы + PK, который одновременно является FK на таблицу суперкласса.

```java
@Entity
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class BillingDetails {
    @Id
    @GeneratedValue(generator = Constants.ID_GENERATOR)
    protected Long id;
    protected String owner;
}

@Entity
public class BankAccount extends BillingDetails {
    @NotNull protected String account;
    @NotNull protected String bankname;
    @NotNull protected String swift;
    // @Id не нужен – наследуется, Hibernate знает как делать JOIN
}

@Entity
@PrimaryKeyJoinColumn(name = "CREDITCARD_ID") // переопределение имени PK в таблице подкласса
public class CreditCard extends BillingDetails {
    @NotNull protected String cardNumber;
    // ...
}
```

**SQL для `select bd from BillingDetails bd`:** `LEFT OUTER JOIN` всех таблиц подклассов + `CASE WHEN` для определения типа:
```sql
select BD.ID, BD.OWNER, CC.EXPMONTH, CC.EXPYEAR, CC.CARDNUMBER,
       BA.ACCOUNT, BA.BANKNAME, BA.SWIFT,
       case when CC.CREDITCARD_ID is not null then 1
            when BA.ID is not null then 2
            when BD.ID is not null then 0
       end
from BILLINGDETAILS BD
left outer join CREDITCARD CC on BD.ID=CC.CREDITCARD_ID
left outer join BANKACCOUNT BA on BD.ID=BA.ID
```

**SQL для `select cc from CreditCard cc`:** простой `INNER JOIN`:
```sql
select CREDITCARD_ID, OWNER, EXPMONTH, EXPYEAR, CARDNUMBER
from CREDITCARD inner join BILLINGDETAILS on CREDITCARD_ID=ID
```

| | |
|---|---|
| ✅ | Нормализованная схема |
| ✅ | NOT NULL работает для всех полей всех классов |
| ✅ | Чёткая эволюция схемы, ограничения целостности |
| ❌ | Сложный SQL, труднее писать отчёты вручную |
| ❌ | Производительность падает при глубоких и широких иерархиях |

> Hibernate не требует `@DiscriminatorColumn` для `JOINED` – использует `CASE WHEN`. Другие реализации JPA могут требовать.

## 6.6. Смешение стратегий: `@SecondaryTable`

Нельзя смешивать `TABLE_PER_CLASS`, `SINGLE_TABLE` и `JOINED` в одной иерархии в чистом виде. Но можно выделить конкретный подкласс в отдельную дополнительную таблицу поверх `SINGLE_TABLE`:

```java
@Entity
@DiscriminatorValue("CC")
@SecondaryTable(
    name = "CREDITCARD",
    pkJoinColumns = @PrimaryKeyJoinColumn(name = "CREDITCARD_ID")
)
public class CreditCard extends BillingDetails {
    @Column(table = "CREDITCARD", nullable = false) // указать таблицу явно
    protected String cardNumber;
    // ...
}
```

**Профит:** поля `CreditCard` выносятся в отдельную таблицу с возможностью `NOT NULL`, при этом основная иерархия остаётся `SINGLE_TABLE`. **Запрос** при полиморфной загрузке будет `LEFT OUTER JOIN`.

## 6.7. Наследование встраиваемых классов

JPA не специфицирует полиморфизм для `@Embeddable`. Hibernate расширяет: встраиваемый класс может наследовать поля от `@MappedSuperclass`.

```java
@MappedSuperclass
public abstract class Measurement {
    @NotNull protected String name;
    @NotNull protected String symbol;
}

@Embeddable
@AttributeOverrides({
    @AttributeOverride(name = "name",   column = @Column(name = "DIMENSIONS_NAME")),
    @AttributeOverride(name = "symbol", column = @Column(name = "DIMENSIONS_SYMBOL"))
})
public class Dimensions extends Measurement {
    protected BigDecimal depth, height, width;
}
```

**Ограничение:** ссылка на экземпляр встраиваемого класса **не может быть полиморфной**. Нельзя объявить поле типа `Measurement` – JPA не знает, `Dimensions` это или `Weight`, так как нет селектора.

---

## 6.8. Выбор стратегии

| Ситуация | Рекомендация |
|---|---|
| Полиморфные запросы/ассоциации не нужны | `@MappedSuperclass` или `TABLE_PER_CLASS` |
| Нужны полиморфизм, подклассы отличаются только поведением, мало новых полей | `SINGLE_TABLE` |
| Нужны полиморфизм, подклассы имеют много обязательных полей (данных) | `JOINED` |
| Очень сложная иерархия с требованием производительности | замерять `JOINED` vs `TABLE_PER_CLASS` на реальных данных |

**Общая рекомендация:** если сложная иерархия создаёт проблемы – возможно, стоит избавиться от наследования и перейти к делегированию.

## 6.9. Полиморфные ассоциации и проблема прокси

Если ассоциация объявлена с `FetchType.LAZY`, Hibernate оборачивает её в **прокси-объект** типа суперкласса. Это ломает `instanceof` и явное приведение типов:

```java
// @ManyToOne(fetch = FetchType.LAZY) — прокси, не реальный объект
BillingDetails bd = user.getDefaultBilling();
assertFalse(bd instanceof CreditCard); // true! bd — прокси BillingDetails
// (CreditCard) bd; // ClassCastException!
```

**Безопасное приведение через `getReference()`:**
```java
CreditCard cc = em.getReference(CreditCard.class, bd.getId()); // без SELECT
// bd и cc — два разных прокси, делегируют одному CreditCard
```

**Лучшее решение – `JOIN FETCH` (eager в запросе):**
```java
User user = em.createQuery(
    "select u from User u left join fetch u.defaultBilling where u.id = :id",
    User.class
).setParameter("id", USER_ID).getSingleResult();
CreditCard cc = (CreditCard) user.getDefaultBilling(); // работает, прокси нет
```

**Для `@OneToMany` на суперкласс** всё работает автоматически – Hibernate генерирует нужный `JOIN` или `UNION` в зависимости от стратегии. Ограничение: сущность суперкласса должна быть `@Entity` + `@Inheritance`, а не `@MappedSuperclass`.

## Главное

- Четыре стратегии: `@MappedSuperclass` (неявный полиморфизм), `TABLE_PER_CLASS` (UNION), `SINGLE_TABLE` (дискриминатор), `JOINED` (внешний ключ)
- `@MappedSuperclass` – не сущность, нет полиморфных ассоциаций и JPQL по суперклассу
- `TABLE_PER_CLASS` – не обязательна по JPA; полиморфизм через UNION ALL
- `SINGLE_TABLE` – лучшая производительность; не может гарантировать NOT NULL для полей подклассов; `@NotNull` проверяется только в runtime
- `JOINED` – нормализованная схема, полный NOT NULL; дорогие LEFT OUTER JOIN при глубоких иерархиях
- `@DiscriminatorColumn` / `@DiscriminatorValue` – всегда указывать значения явно для `SINGLE_TABLE`
- `@DiscriminatorFormula` (Hibernate) – вычисляемый дискриминатор через SQL-выражение, когда нет отдельного столбца
- `@SecondaryTable` – выделить конкретный подкласс в отдельную таблицу поверх `SINGLE_TABLE`
- `@Embeddable` может наследовать от `@MappedSuperclass`; ссылка на встраиваемый тип не может быть полиморфной
- `FetchType.LAZY` + полиморфная ассоциация → прокси суперкласса, `instanceof` и cast не работают → использовать `JOIN FETCH` или `em.getReference()`
